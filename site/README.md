# attackledger.com

Static site: `index.html` plus a sample report that anyone can verify offline.

- `sample-report.html`, `sample-report.json`: generated by `tools/build_site.sh` from the
  demo stack (fictional `*.client.test` hosts). Do not edit them by hand.
- `verify_report.py`: a copy of `tools/verify_report.py`, refreshed by the same script,
  with `digicert-trusted-root-g4.pem` from `tools/tsa-roots/` for the timestamps.
- To rebuild the demo from scratch, with fresh volumes and the same `ATTACKLEDGER_API_TOKEN`
  in the environment of every step:
  1. Start the demo stack (`tools/demo/compose.override.yml`, the command is at its top).
  2. `tools/demo_stack.py`: the seed (four engagements), the scope rules, an evidence import
     on "Client web app" by a demo tester (the HAR and Burp files in `tools/demo/imports/`,
     made from lab answers by `tools/demo/make_imports.py`), then a full pipeline run against
     the lab.
  3. `tools/demo_sign.py` inside the demo API container: a demo reviewer signs the closed
     lanes; DigiCert timestamps them (only hashes are sent).
  4. `tools/demo_retention.py` inside the demo API container, after the signatures: the demo
     owner sets a retention date on "Client web app" and deletes the content of "Client
     portal 2025".
  5. `tools/build_demo.sh http://localhost:8098 2 3 1 4` and `tools/build_site.sh`.

  ```bash
  export ATTACKLEDGER_API_TOKEN=...      # the demo API's token
  python3 -I tools/demo_stack.py http://localhost:8098
  docker exec -i -e DEMO_TOKEN="$ATTACKLEDGER_API_TOKEN" attackledger-demo-api-1 python - < tools/demo_sign.py
  docker exec -i -e DEMO_TOKEN="$ATTACKLEDGER_API_TOKEN" attackledger-demo-api-1 python - < tools/demo_retention.py
  tools/build_demo.sh http://localhost:8098 2 3 1 4 && tools/build_site.sh
  for f in site/demo/reports/*.json; do python3 -I tools/verify_report.py "$f" --tsa-root tools/tsa-roots/digicert-trusted-root-g4.pem; done
  ```

  The export also writes each imported entry's redacted parts to `demo/inbox/` and each
  engagement's gateway log into `demo-data.json` (the app has no view of the log yet).
- `verify.html` (served at `/verify`): the public verifier page. Generated by
  `tools/build_verify.sh` from `web/src/verify_page.html` and `web/src/verify_page.ts`, with
  the shared verifier module `web/src/verify_report.ts`, the fonts and the roots in
  `tools/tsa-roots/` all inline. Do not edit it by hand: its CSP carries the hashes of its
  inline script and style, and `tools/build_pages.sh` refuses a page whose hashes do not
  match. After changing the module or the page, run `tools/build_verify.sh` and
  `tools/verifier_equivalence/run.sh` (see `docs/VERIFIER.md`).
- `demo/`: the web app built in read-only demo mode (`VITE_DEMO=1`) with a snapshot from a
  demo stack (`tools/build_demo.sh`). Fictional hosts only; recon comes from a lab run.

Deployed to Cloudflare Pages, project `attackledger` (first deployment 2026-10-09).
To publish a new version (needs `npx wrangler@3.114.0 login` once):

```bash
tools/build_pages.sh
npx wrangler@3.114.0 pages deploy dist/pages --project-name attackledger --branch main \
  --commit-hash "$(git rev-parse HEAD)" --commit-dirty=true
```

`404.html` is the not-found page; without it Pages would answer every unknown path with the
home page.
