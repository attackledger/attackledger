AttackLedger For auditors · October 2026 · version 0.8.0 (preview)

Proof of what a security test covered, that you check yourself.

A penetration test report says what was found. It rarely shows what was checked. AttackLedger records every check as evidence, a named reviewer signs off each part of the test, and you verify the report offline without trusting the tester's tools.

The problem

An auditor usually gets a list of findings and a methodology statement. There is no record of which hosts were tested, which checks ran, what the evidence was, or who signed off. "No findings" can mean the area was sound, or that it was never reached.

AttackLedger follows an audit rule: a control without evidence is a control that was not performed. A test area counts as done only when it has a receipt.

What an auditor gets

  • The rules: scope and the recorded authorization.
  • Coverage per host and lane: each lane (one test area on one host) is a checklist, such as the OWASP WSTG. Each item has evidence or a written not-applicable reason, shown apart and never counted as evidence.
  • Control mapping status: PCI DSS v4.0.1, ISO/IEC 27001:2022 and DORA; per control, how many mapped items are receipted, and the strength: partial or supporting, none full.
  • Who signed what, and when: each receipt is signed with a key in the reviewer's browser and timestamped (RFC 3161). The change history shows who held the reviewer role and which scope was in force.

How verification works

  1. Run the verifierpython3 verify_report.py report.json --require-history. Python standard library only, no network, no shared code with AttackLedger. Or use attackledger.com/verify: nothing is uploaded.
  2. Compare fingerprintsGet the reviewers' and the server's seal key fingerprints from the tester by another channel, and compare them with the report.
  3. Read what was verifiedCheck the seal time, the engagement settings (separation of duties, signatures required), and for HTML compare the page with the verifier's summary.

Checked: the report body hash, the evidence chain, each receipt against its rebuilt manifest, each signature and timestamp, the change history and the server's seal.

What it does not prove

  • That the operator is honest. The server's seal is its own statement; the reviewers' signatures are the evidence of the review.
  • That the evidence is genuine, or that the test was complete or good.
  • That the reviewer really reviewed: a signature is a statement.
  • Compliance. The mappings are indicative, reviewed by an AI assistant (Claude) against public sources, not by a qualified assessor. DORA TLPT is not mapped.
  • Independent assurance of the tool. No independent third party has tested it; the security review was the author's own, with AI agents.
